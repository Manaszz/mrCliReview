# gitlab-mr-opencode-review

## Purpose

Process a GitLab `merge_request` webhook event inside Hermes and produce one Markdown code review comment in the same MR using OpenCode for the actual analysis.

This is the **v1 review-only flow**.
Do **not** modify code, create fix branches, or open extra merge requests.

---

## Required environment

The runtime must provide these variables:

- `GITLAB_URL`
- `GITLAB_TOKEN`
- `HERMES_MR_ROOT`
- `OPENCODE_MODEL` (optional)

Expected defaults:

- `GITLAB_URL=https://gitlab.example.com`
- `HERMES_MR_ROOT=/opt/mrCliReview/runtime/mr-review-workspaces`

---

## Inputs expected from webhook prompt

Read the values that Hermes injected from the webhook route prompt:

- `project_id`
- `project_path`
- `mr_iid`
- `mr_title`
- `mr_description`
- `mr_action`
- `source_branch`
- `target_branch`
- `mr_url`
- `last_commit_sha`

If any of `project_id`, `mr_iid`, `source_branch`, `target_branch` are missing, stop and report a clear error.

---

## Allowed actions

Only continue when `mr_action` is one of:

- `open`
- `update`
- `reopen`
- `approved`

For all other actions, do nothing except log that the event was intentionally ignored.

---

## Execution steps

### 1. Prepare workspace

Create a stable workspace under:

`$HERMES_MR_ROOT/<project_id>/mr-<mr_iid>`

Inside it create:

- `repo/`
- `artifacts/`
- `artifacts/diff.patch`
- `artifacts/opencode-prompt.md`
- `artifacts/opencode-output.md`
- `artifacts/final-comment.md`

### 2. Resolve project metadata from GitLab API

Call:

- `GET $GITLAB_URL/api/v4/projects/<project_id>`
- `GET $GITLAB_URL/api/v4/projects/<project_id>/merge_requests/<mr_iid>`

Use `PRIVATE-TOKEN: $GITLAB_TOKEN`.

Use the GitLab API response as source of truth for:

- repo clone URL
- source branch
- target branch
- current MR title
- current MR description
- web URL

If webhook payload conflicts with fresh API data, trust the API.

### 3. Clone or refresh repository

If `repo/.git` does not exist:

- clone the repository into `repo/`

If it exists:

- `git remote -v`
- `git fetch --all --prune`
- hard reset local review branch state if needed

Use HTTP clone URL from GitLab project metadata.

### 4. Checkout MR source branch and fetch target branch

Inside `repo/`:

- fetch source branch
- fetch target branch
- checkout source branch
- reset to `origin/<source_branch>`

Then build diff against target branch:

`git diff --binary origin/<target_branch>...HEAD > artifacts/diff.patch`

If the diff is empty:

- write a short note that no effective code changes were detected
- publish that note to GitLab
- stop

### 5. Build OpenCode prompt

Read template file:

`templates/opencode-review-prompt.md`

Substitute placeholders:

- `${PROJECT_PATH}`
- `${MR_IID}`
- `${MR_TITLE}`
- `${MR_DESCRIPTION}`
- `${SOURCE_BRANCH}`
- `${TARGET_BRANCH}`
- `${MR_URL}`
- `${DIFF_PATH}`

Write resolved prompt to:

`artifacts/opencode-prompt.md`

### 6. Run OpenCode

Use the built-in `opencode` capability if available. If you need shell fallback, use non-interactive CLI mode.

Preferred shell fallback:

```bash
opencode run --file artifacts/opencode-prompt.md --format text
```

If you need an explicit model and it is configured:

```bash
OPENCODE_MODEL="$OPENCODE_MODEL" opencode run --file artifacts/opencode-prompt.md --format text
```

Save the raw result to:

`artifacts/opencode-output.md`

### 7. Normalize final comment

Create `artifacts/final-comment.md` with this wrapper:

```markdown
## AI MR Review

<normalized OpenCode result>

---
Generated by Hermes + OpenCode
```

Rules for normalization:

- keep Markdown
- remove duplicated headings if necessary
- keep output concise and useful
- prioritize blocking issues over style nitpicks
- if there are no serious issues, say so clearly

### 8. Publish note to GitLab

Run helper script:

```bash
bash scripts/post_gitlab_note.sh <project_id> <mr_iid> artifacts/final-comment.md
```

If publishing fails, preserve all artifacts and return a clear error.

---

## Review policy

OpenCode must focus on:

1. correctness and bugs
2. security risks
3. breaking behavior changes
4. architecture or layering violations
5. dangerous performance regressions
6. missing tests where the change is risky

Avoid wasting output on:

- trivial formatting
- personal style preferences
- speculative rewrites without concrete benefit

---

## Explicit non-goals for v1

Do **not**:

- change repository files
- commit anything
- push branches
- create fix MRs
- create refactoring MRs
- auto-approve or auto-reject the MR

This skill is **review only**.
